# 进程归属监控引擎（① 地基）设计

> 这是"装机守卫"大愿景三个独立项目中的第一个（地基）。②装机守卫、③长期深度追踪各自另出设计，都建立在本引擎之上。
>
> **状态**：① 引擎已实现（0.9.0，开发中，未发布），②③另行设计。本文正文仍为 ① 的设计依据，实现细节以代码与 CHANGELOG 为准。

## 背景与目的（为什么）
用户要一套能力：知道"**哪些文件/注册表/服务是某个软件自己弄出来的**"，以便 (a) 卸载时精确清掉它的一切残留——包括藏在它名字/安装目录**之外**的（如 360 往 U 盘根目录放文件夹）；(b) 识别并去掉捆绑；(c) 对可疑程序长期追踪。

**快照法（装前装后拍照取差集）被否决，理由成立**：它只看"前后多了什么"，分不清新文件是用户自己建的还是软件建的，恢复/清理时可能误删用户数据。

替代方案经探针验证可行（2026-10-22 ETW spike）：用 **ETW 在用户态**（无内核驱动、无 Hyper-V、不惹反作弊）按"哪个进程创建了哪个文件"归属，**能天然区分用户自建 vs 软件自建**。探针实测：子进程树建的文件标 CHILDTREE、探针自身("用户")建的标 SPIKE、其他进程标 OTHER，区分正确；空闲约 200 文件事件/秒，开销很低；仅需管理员。本项目把该结论做成可靠引擎。

## 范围
- 本设计**只覆盖 ①**：监控引擎本身（起止、按进程归属、足迹采集与存储、安全）。
- ②（装机守卫：检测安装、异常标红、捆绑识别与去除）、③（长期深度追踪）各自单独设计。
- ① 作为**可选模块**：轻量版（现有 App）不带、不常驻；用户显式启用"监控模块"才运行。

## 目标
一次"监控会话"里，把一个目标进程树（根 = 用户发起的某次安装/运行）在此期间对系统做的改动，**按进程归属**记录成一条"足迹"：
- 新建的文件/目录（真·创建，非单纯打开）
- 新建/改写的注册表键值
- 新装的服务、驱动、计划任务、开机自启项
- 进程树本身（根 + 子孙，含 exe 路径）
归属精确：只记目标进程树干的；用户或其他进程干的不记。足迹持久、可被 ②③ 与卸载器读取。

## 非目标（本期 ① 不做）
- 不做异常判定、捆绑识别、标红报告（→ ②）。
- 不做"恢复到安装前"的实际删除/回滚（① 只产出足迹；删除复用卸载器 ②）。
- 不做常驻的"所有安装都自动监控"（① 提供能力，②决定何时开）。
- 不做网络行为监控（本期只文件/注册表/进程/服务/驱动）。

## 反目标（即使技术跑通也算失败）
- 把用户自己创建的文件误归给软件——绝不允许（这是放弃快照的全部理由）。
- 让提权引擎能被诱导执行任意程序或删任意路径（守住卸载器已确立的安全不变量）。
- 让轻量版用户被迫承担监控开销（必须可选、默认关）。
- 吃性能到影响日常/游戏，或触发反作弊封号。

## 约束
- Windows 10/11、.NET 10、TreatWarningsAsErrors、全中文面向用户、提交不加 Claude 署名。
- ETW 内核会话需管理员 → 复用现有提权助手模型（计划任务 + 原生干净启动器 + 命名管道 + SID 校验 + ACL/防冒充）。
- 复用卸载器已做结实的存储设施（原子写 + 跨进程命名 Mutex 的 JSONL），footprints 另开存储区。
- ETW 消费用 Microsoft.Diagnostics.Tracing.TraceEvent（探针验证 3.1.9 可用；正式选版 ≥2 周，并处理其传递依赖漏洞告警 NU1903）。

## 架构（已决定的部分；标注"我的默认决定"）
### 宿主与发起
- 监控引擎跑在**提权助手新增的"监控模式"**里，不另造服务；复用干净启动器/管道/SID/ACL。
- 【我的决定】监控是长时间、流式的，与现有"单请求单响应"管道不同 → 给助手加一个**长连接监控通道**（仍每用户命名管道 + 同样 ACL/防冒充）：App 订阅事件流（发现了哪些项）与最终足迹，支持取消/断线。
- 【我的决定】**由引擎在监控下启动目标**：App 把"用户选的、要监控地运行的安装包路径"经结构化请求交给助手；助手在 ETW 会话就绪后 CreateProcess 拉起它、记下根 PID，据此建进程树（根 PID 可靠，不靠猜）。
  - 安全：此处要运行的程序路径是**用户在 App 里明示选择的安装包**（等价于用户自己双击它），助手只 CreateProcess 这一个用户指定文件、全程监控，**不执行其它任何东西**。这与卸载器"命令只从注册表自取"是两种场景，但同样做到"不执行任意来源的命令"。

### 采集（ETW providers）
- Kernel：FileIOInit（文件创建/打开）、Registry（注册表）、Process（进程起止，建树）、ImageLoad/Driver（抓驱动/服务加载）。
- 【我的决定】文件按"真·新建"过滤：用 FileIOCreate 的 CreateDisposition/CreateOptions 区分"创建新文件"与"打开已有"，只记前者（含写入/重命名到新位置）。
- 进程树：ProcessStart 的 ParentID 建树，根 = 我们拉起的 PID，递归纳子孙；处理 PID 复用（会话内时间窗 + 进程生命期）。

### 足迹模型与存储
- 一条 MonitorFootprint：Id、软件标识（关联根进程/其装出的卸载登记）、起止时间、Entries[]（类型 = 文件/目录/注册表键/服务/驱动/计划任务/自启，OriginalPath，创建它的 PID 与 exe，首次出现时间）。
- 【我的决定】复用卸载器 BackupStore 同款设施（JSONL + 原子写 + 跨进程 Mutex），新开 footprints 区；只存路径/键名/元数据，**不存文件内容**。
- 大小有界：一条足迹正比于"这次安装动了多少项"，不随时间长涨（① 是会话制）。

### 安全不变量（必须守住）
- 引擎提权，但对外只接受结构化请求：开始监控（带用户选的安装包路径）/停止/取足迹。不接受"执行任意命令/删任意路径"。
- 启动目标仅为用户在 App 明示选择的那一个文件；助手不另跑。
- 归属只认目标进程树；越界 PID 的动作一律不记。
- **本期 ① 只采集、只产足迹、不做任何删除** → 即便归属有误也不会在 ① 里造成破坏；删除风险留在 ②/卸载器环节（那里有分级 + 备份 + 可恢复兜底）。

## 留给实现者
- ETW 会话可靠起停、重复会话清理、丢事件/缓冲溢出处理。
- CreateDisposition 精确区分新建 vs 打开的具体字段与边界。
- 进程树 + PID 复用的健壮处理。
- 长连接监控通道协议（流式事件 + 最终足迹 + 取消/断线），复用管道 ACL/防冒充。
- 足迹存储 schema 与 BackupStore 设施复用。
- 可选模块的启用/禁用与状态显示（设置页）。
- 性能实测（真实安装包下的事件率与 CPU/内存），评估是否需内核侧 PID 过滤降负载。

## 决定（2026-10-22 builder-check 之后敲定；与上文冲突处以此为准）

### 用户拍板
- **归属分级**：直接进程树干的 = 「确定」；MSI/服务/驱动/计划任务等由系统进程（msiexec/msiserver、SCM/services.exe、TrustedInstaller）代办、但在监控窗口内能关联回软件树发起的 = 「可能」（比「确定」低一档）；关联不上的越界动作 = 不记。每条足迹项带 confidence（确定/可能）。②在删除时对「可能」档默认需用户确认。——这修正了上文"越界 PID 一律不记"的说法。
- **重启续传**：本期 ① 不支持。监控期间检测到系统重启 → 该足迹标「不完整」，留给后续 / ③。
- **模块形式**：装在同一个包、**默认关、不常驻**；用户在设置页手动启用（启用时一次 UAC 注册"监控模式"，复用现有提权助手的计划任务/部署，AgentSetup 扩展）。轻量版用户不受影响。

### 我的决定（builder-check 其余项）
- **启动模型（修正上文"由引擎启动目标"）**：安装器在**用户身份**下运行，保证 %APPDATA%/HKCU 归到用户名下、安装器 UI 与 shell 集成正常、"用户 vs 软件"的归属不被污染。流程：App 请求「开始监控」→ 助手起好 ETW 会话并回执就绪 → App 在用户上下文启动所选安装器（或助手用用户主令牌 CreateProcessAsUser 启动），把根 PID 告知助手 → 助手据此建进程树。ETW 先于安装器动作就绪，期间事件先缓冲，拿到根 PID 后回溯归属（不漏事件）。校验：只接受用户在 App 明示选择的、本地盘上的 .exe/.msi。
- **足迹完整性 / 防伪造（安全要点）**：足迹由提权助手写入**只有管理员可写、ACL 保护的目录**，普通用户只读；杜绝普通用户伪造足迹、将来被 ② 拿去删任意路径（守住"提权引擎不能被诱导删任意路径"）。App 经助手只读回。复用 BackupStore 的原子写 + 跨进程 Mutex，但存储位置移到受保护区。有保留上限、可删。
- **路径**：NT 设备路径 → Win32 规范化；对可移动/非系统卷额外记**卷序列号/GUID**，U 盘换了盘符仍能定位（对应 360 往 U 盘丢文件夹的案例）。
- **注册表**：只记键/值名 + 是否新建（CreateKey vs OpenKey / 存在性预检），不存值内容。
- **通道**：监控走**独立命名管道**（自己的实例，不占用 Upgrade/RemoveResidue 那条），升 `AgentProtocol` v3。App 断开 → 助手继续记录、足迹不丢、App 可重连；结束条件 = 用户「停止」/ 进程树空闲超时 / 达最大时长。
- **会话单例与冲突**：一次只允许一个监控会话；若内核日志会话被别的工具（如 Process Monitor）占用 → 明确报错请用户关掉它，**不抢占**。
- **身份关联**：足迹用它记录到的新 Uninstall 键关联到软件；便携/失败安装可留「未关联」，待 ② 匹配。

## 记什么、不记什么（信噪与完整性 —— 2026-10-22 用户强调，本节与上文冲突处以此为准）

用户的要求：**既不能记无效的噪声，也不能漏记该留的项**。两头都靠下面的规则兜住。

### 原则：不存原始事件流，存"净效果"
ETW 流里绝大多数是噪声（打开、读取、临时文件来回建删）。引擎**全程只在内存里累积**，在监控结束时做一次**净效果收尾（reconciliation）**才落盘足迹：
- 本次**建了又被自己删掉**的（create→delete 净零）→ **丢弃**，不进足迹。
- 建完并在收尾时**仍存在**（文件/目录/键/服务/驱动/任务/自启实际还在）→ **保留**。收尾时逐项**复验存在性**，存在才写——避免写进早已不在的"幽灵记录"（无效记录的主要来源）。
- 改写**已存在**的项 → 保留，但打 `新建 vs 修改` 标记（卸载/恢复时区别对待：新建的可删，原有的只还原）。
- 同一落点的重复写入**合并成一条**（去重），不按事件条数堆。

### 落点过滤：只有"驻留位置"才算足迹
只有落在**长期驻留位置**的才记为软件足迹：Program Files、ProgramData、%LOCALAPPDATA%/%APPDATA%、HKLM/HKCU 的软件与 Uninstall/服务/驱动/Run 等、计划任务、以及可移动卷上的驻留目录（带卷序列号，对应 360 丢 U 盘的案例）。
明确**不记**（规则黑名单，视作噪声）：
- %TEMP%/%TMP%、安装器自解压的临时目录、Windows\Temp；
- OS 自身产物：Prefetch、WER、事件日志、字体缓存、`.etl`/`.log` 之类系统噪声；
- 纯读取/打开、无驻留结果的动作。
落在**既非黑名单也非明确驻留区**的模糊位置 → 记为 `可能`（低一档置信度），交给 ② 让用户定夺,不直接当成确定足迹,也不悄悄丢。

### 完整性标记：漏记要"被标出来"，绝不悄悄漏
把三类"可能漏"显式标成「不完整」写进足迹头，让 ②/卸载器知道这条足迹不可全信、需提示用户补扫，而不是当成完整足迹误导删除：
1. **ETW 缓冲溢出丢事件**：读 TraceEvent 的 `EventsLost`，>0 → 标「不完整(丢事件 N)」。
2. **代办动作关联不全**：MSI/服务/驱动由系统进程代办（已按"可能"档记），若其中有关联不回软件树的 → 标「可能有代办项未归属」。
3. **监控提前结束**：用户中途停止、达最大时长、或检测到系统重启（本期不续传）→ 标「不完整(未跑到安装自然结束)」。
完整收尾（无丢事件、进程树自然退出、无模糊残项）才标「完整」。

### 验收（实现者必须证明）
- 建了又删的临时文件**不**出现在足迹里；装完仍在的目标文件**一定**出现。
- 跑一个真实安装包：足迹项数 ≈ 人工核对的驻留改动数（既不虚高也不缺项）。
- 人为制造丢事件（高并发压测）→ 足迹被标「不完整」，而非静默缺项。

## 真机冒烟后的修订（2026-11-16，与上文冲突处以此为准）

用刁钻的无害假安装器在真机（反作弊在跑）上复现了四个缺口，采集方式据此调整：

- **采集源**：不再用传统内核提供程序（NT Kernel Logger / system logger），改用三个内核清单提供程序 Kernel-File、Kernel-Registry、Kernel-Process，普通会话名启用。原因：传统文件创建事件只有"打开意图"，分不清新建和打开已有文件；改名事件拿不到新名；注册表新建键不区分新建/打开。清单提供程序在这几处都给了准确字段，而且不占 NT Kernel Logger 与有限的 system logger 槽位，天然与反作弊并存。
- **文件新建**：只认 CreateNewFile（磁盘上真的新建）。打开已有文件一律不记——这是保护用户原有文件的关键。
- **改名**：用 RenamePath 的新路径，配合之前打开事件里的文件对象找回旧名，把旧名那本账整本搬到新名，"是否本次新建"跟着文件走；目录改名连同已记账的下级文件一起搬。
- **注册表**：CreateKey 的 Disposition 判断是否真新建；订阅 OpenKey，按"基键对象 + 相对名"自行拼出写值事件所在键的全路径；写值按旧值的类型/大小判断是否新值。树内改动拼不出路径时标「不完整」，绝不编造路径。系统自己写的注册表噪声（后台活动调节器、UserAssist、MuiCache 等）不记。
- **服务 / 驱动 / 计划任务**：由服务控制管理器、任务计划服务等系统进程代写，按进程树归不到安装器。改为在监控开始与结束各取一次系统名册求差集，记为「可能」档；取名册失败标「不完整」。这不违背否决快照法的理由——那条针对的是用户文件，而这几类是用户不会在装软件的几十秒里手建的系统名册。驱动不再依赖映像加载事件。
- **正常完成**：根进程树整体退出即收尾、标「完整」；Idle / Max / 用户停止 / 未收到根 PID 仍为「不完整」兜底（Ruling-9）。
- **SoftwareKey**：之前为空是因为新建键事件抓不到；现在新建的 `...\Uninstall\<子键>` 能带完整路径记入，按 Ruling-3 识别。覆盖安装时 Uninstall 子键早已存在、本次只改写值，SoftwareKey 仍为 null——那个键本就不是这次装出来的，留给 ② 按其他线索关联。
- **已知待办**：监控安装尚无界面入口（何时监控、如何选择安装包，属于 ② 的设计）。

## 0.9.1 修订：独立评审后的"新增"判定（2026-11-27，与上文冲突处以此为准）

足迹将来会被拿来删东西，所以"新增"只在能确定时才标：

- **键的默认值**是值、不是键（值名为空串，路径以 `\` 结尾，界面显示"（默认）"）。写已有键的默认值不再让该键以"新建"进足迹；删默认值也不再抵消新建的键。
- **改名的目标原来有没有文件**：真机实测，`MoveFileEx` 带"替换已有"覆盖用户原有文件时，被替换的文件不留任何事件，创建时间也**不继承**（文件名隧道只在"先改名 / 删掉原文件、再放新文件"时生效）。因此改名搬到一个本次监控里从没记录过的路径时，**只有落在本次新建的目录里才算新增**，否则只算改动——宁可将来少删，不误删。为此开始记录本次新建的目录（目录本身不进足迹）。
- **原有文件被改名挪走**（典型是先改成 `.bak` 再放新文件）：在原路径留一笔"动过"，之后同一路径上的新建只算改动，不依赖文件名隧道。另保留"创建时间早于监控开始 → 不算新增"作为额外兜底。
- **空 REG_NONE 值**（类型 0、大小 0，如文件关联的 OpenWithProgids）：写入前后都是空 REG_NONE 时，"原本不存在"与"原本就有"分不清，只有所在键是本次新建的才算新增。
- **已知限制**：已有键下原本就有一个空 REG_NONE 值、安装器把它改写成别的类型或写入数据时，仍会被判成新增（旧值类型和大小都是 0，与"原本不存在"无法区分）。不再收紧，是因为代价是把所有"已有键下真正新增的值"（如 Run 键里新加的自启项）都降成改动，而那正是装机守卫识别捆绑最需要的信号。这种情况极少见；将来按足迹删除时，已有键下的值一律要求用户确认。
- **改名查不到原文件名**（采集侧对象表里没有）时，树内的改名会把足迹标"不完整"。
- **引擎版本号**：足迹带 `EngineVersion`（当前 2）。0.9.0 采集的足迹为 0，其"新增"标记有上述缺陷；界面会提示"仅供参考"，将来按足迹删除时必须拒绝使用。
- **二次复审补充**：新建目录的记录在该路径被删除时作废（删除事件不带目录标志，所以任何删除都清该路径及其下级的记录）；从别处改名搬进新建目录的目录记为"外来目录"，往上找父目录时先碰到它就不算"在新建目录里"；只记树内/代办进程建的目录。改名合并进目标已有记录时，除非那条记录最后一个动作是删除（确定此刻为空），否则同样要求落在新建目录里才算新增。目录整体改名带着下级搬时，下级不加这个要求（目录改名不可能覆盖已有目录）。
- **待真机验证（② 按足迹删除之前必须完成）**：上面的判断依赖"建目录时 Kernel-File 会发 CreateNewFile（事件 30），且 CreateOptions 带 FILE_DIRECTORY_FILE（0x1）"。若真机不是这样，"先写临时文件再改名"的安装器装出来的文件会全部记为"改动"而不是"新增"——不会误删，但会让将来的精确卸载留下残留。用 Inno Setup 一类的安装器在测试虚拟机里实测。
