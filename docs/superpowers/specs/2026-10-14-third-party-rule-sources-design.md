# 设计：第三方规则源（用户自定义规则订阅）

状态：已与用户确认设计方向（2026-10-14）。本文件是本功能的权威设计，是对
`2026-10-13-rule-subscription-design.md`（官方规则在线刷新）和主设计文档 §8 的扩展。

## 1. 目标与定位

本工具的定位：**保证开箱即用的基础功能，同时给足深度自定义的自由**——类似 GKD、壁纸引擎那种"官方给一套、社区/个人可以随意扩展和覆盖"的玩法。

第三方规则源让用户订阅自己信任的规则文件（社区维护的、或自己给内部软件写的），用来：认出官方规则库没收录的软件、补后台项目说明、显示"有新版"、以及一键更新。

### 核心原则
- **默认安全**：第三方默认不覆盖官方；危险口子都默认关、要用户亲手开。
- **充分自定义**：用户可以手动允许第三方规则覆盖官方规则（含 `signer`），实现深度客制化。
- **不碰的底线**：无论怎么自定义，从第三方规则安装前都有**醒目警告**，且安装器**照旧校验下载包的数字签名**与规则声明的 `signer` 一致——"再怎么自定义，也不会被静默装东西"。

### 本轮范围
- 添加/删除/启用/停用第三方源；每源「允许覆盖官方规则」开关；全局总开关。
- 下载（HTTPS）、解析、按信任与覆盖设置加载第三方规则。
- 「规则」页的第三方源管理 UI；所有消费性开关的确认提示。

### 本轮明确不做
- **防篡改 / 签名验证**（用户决定第三方只走 HTTPS，不验签；留给以后或贡献者）。
- 源的清单(index)格式、源的自动发现、每条规则级别的单独开关（只做到每源粒度）。

## 2. 源模型

- **一个源 = 一个指向 YAML 文件的 URL**。
- 该 YAML 文件可含**一条或多条规则**：多条用 YAML 文档分隔符 `---` 隔开（现有官方规则文件都没用 `---`，向后兼容）。
- 传输只走 **HTTPS**，**不验签**。下载失败、解析失败只影响该源。
- 作者零工具：写好 yaml、托管到任意 https 地址即可。

## 3. 信任与覆盖

`RuleTrust { Official, ThirdParty }` 已存在。扩展加载规则：

- **默认**：第三方规则**不覆盖**官方同 `id` 规则（现有 `RuleSetLoader` 已是此行为）。
- **每源开关 `AllowOverrideOfficial`（默认关）**：打开后，该源的规则在同 `id` 冲突时**胜过官方规则**（包括覆盖官方的 `signer`）。
- 冲突优先级（同一次加载内）：
  1. 开了覆盖的第三方源 > 官方 > 没开覆盖的第三方源。
  2. 多个"开了覆盖"的第三方源撞同一 id：按源的添加顺序，先到先得，其余记一条警告忽略。
  3. 没开覆盖的第三方源撞官方 id：忽略该第三方规则（记警告），官方保留。
- 每条第三方规则在加载后需**带上它的来源**（源 URL / 源显示名），供安装前警告展示。

## 4. 安全护栏（底线，不随自定义改变）

- **安装前强警告**：当一次更新来自第三方规则时，确认对话框必须醒目显示：
  「此更新来自**未经审核的第三方规则源**」+ 来源 URL + 规则声明的发布者(`signer`)，用户确认才继续。
- **签名校验不放宽**：`RuleInstaller` 照旧下载安装包并校验其数字签名与规则 `signer` 一致，第三方规则也不例外、不跳过。
- 这两条对"开了覆盖"的第三方规则同样生效。

## 5. 开关与确认提示

三个开关：
- **全局「启用第三方规则源」**（设置项；默认见下）。关掉它 = 回到纯官方规则状态。
- **每源「启用/停用」**。
- **每源「允许覆盖官方规则」**（默认关）。

**消费性改动必须弹确认框说明，不能点一下直接生效**（用户明确要求）：
- **关闭**全局总开关、**停用**某个源：确认框说明"这会停用你添加的第三方规则，相关软件可能变回认不出/不再提示更新"。
- **打开**某源「允许覆盖官方规则」：确认框说明"该源的规则将覆盖官方规则（含发布者校验目标），请确认你信任这个源"。
- 低风险动作（添加源时填 URL、关闭"允许覆盖"回到安全、删除一个源）可不强制二次确认，但删除源要普通确认（防误删）。

默认值：全局「启用第三方规则源」**默认开启**（因为添加一个源本身已是用户的明确动作，没加源时这个开关无实际影响）；每源「启用」在添加时默认开；每源「允许覆盖」默认关。

## 6. 存储

- **源列表**：`%APPDATA%\UpdateHelper\rule-sources.json`，内容为一个数组，每项：
  `{ id, url, note, enabled, allowOverrideOfficial }`（`id` 为本地生成的稳定标识，如 url 的哈希；`note` 用户备注）。文件顶层再带一个全局布尔 `thirdPartyEnabled`（即本文件形如 `{ "thirdPartyEnabled": true, "sources": [ … ] }`）。
- **下载缓存**：`%LOCALAPPDATA%\UpdateHelper\thirdparty-cache\<源id>\rules.yaml`（原样存下载到的 YAML）。失败时保留上次成功的缓存。
- 读写坏数据不抛，回退到"无第三方源"。

## 7. 同步

- 跟官方规则**同一个调度**：每日自动一次 + 「规则」页「立即同步」。
- 对每个**启用**的源：HTTPS 下载 → 存缓存 → 解析。某个源任何失败（网络/解析/空）**只跳过它并记录**，不影响官方规则和其它源。
- 同步全程后台线程，不卡界面，不弹错误框（状态在「规则」页显示）。

## 8. 加载链路

- 现有：`RuleSetLoader.Load(sources)` 接收多个 `RuleSource(Directory, Trust)`，官方优先、坏文件跳过、重复 id 去重。
- 扩展：
  - `RuleSource` 增加 `AllowOverrideOfficial`（和一个来源标识，供规则标注来源）。
  - 加载顺序与去重按 §3 的优先级调整。
  - 第三方源的"目录"就是它在 `thirdparty-cache` 下的目录；一个源的 YAML 可能含多条规则 → 第三方加载要支持把一个文件按 `---` 拆成多条解析（官方单文件单规则的行为不变）。
- `RealBackend` 组装 sources 时：官方目录（现有择新逻辑）+ 所有"已启用"的第三方源目录（带各自的 AllowOverrideOfficial）。

## 9. 界面（「规则」页）

在现有官方源卡片下方加「第三方规则源」区：
- 顶部：全局「启用第三方规则源」开关（关闭走确认框）+ 一句 **"第三方源未经审核，内容和更新包都由对方负责，风险自负"** 的常驻提示。
- 列表：每个源一行——备注/URL、规则数、上次同步状态、「启用」开关、「允许覆盖官方」开关（打开走确认框）、删除按钮（普通确认）。
- 底部：「添加源」——输入 URL（可选备注），校验是 https 再加入；加入后立即尝试同步一次。
- 所有确认框用 WPF-UI 的对话框（**不触发**任何会阻塞的系统级弹窗）。

## 10. 测试

- 加载优先级：官方 vs 第三方（不覆盖/覆盖）、多个覆盖源撞 id、坏 YAML 跳过、一个文件多条(`---`)拆分。
- 源配置存取：rule-sources.json 往返、坏数据回退、enabled/allowOverride 字段。
- 同步：假下载器——某源失败只跳过它、其余正常；缓存保留上次成功。
- 第三方来源标注：安装前能拿到"第三方 + 源 URL + signer"用于警告。
- ViewModel：开关状态→确认提示文案；列表渲染；添加校验 https。
- 安装护栏：第三方规则走安装器仍校验签名（复用现有 RuleInstaller 测试思路，断言不跳过）。
- 真实网络不进单测；真机端到端手动验一次（加一个源、同步、看到规则、覆盖开关、安装警告）。

## 11. 与现有代码的落点

- 复用：`RuleTrust`、`RuleSource`、`RuleSetLoader`（扩展优先级与多文档解析）、`RuleParser`、`IDownloader`/`HttpDownloader`、现有「规则」页与同步调度、`RuleInstaller` 的签名校验。
- 新增：源配置存储、第三方同步逻辑、第三方缓存、规则来源标注、安装前警告的第三方分支、「规则」页第三方 UI 与确认框。
- 不涉及提权，与搁置的后台助手无关。
- 偏离旧 spec：`2026-09-30` 主文档 §8 曾写"第三方规则不能放宽官方 signer"——本设计按用户新决定改为"**默认不覆盖，用户手动开启后可覆盖**"，并以安装前强警告 + 签名校验兜底。
