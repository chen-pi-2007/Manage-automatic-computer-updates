# 设计：第三方规则源（用户自定义规则订阅）

状态：已与用户确认设计方向（2026-10-14），并经一次对照代码库的独立评审后补精确（2026-10-14）。
本文件是本功能的权威设计，是对 `2026-10-13-rule-subscription-design.md`（官方规则在线刷新）
和主设计文档 §8 的扩展。

## 1. 目标与定位

本工具的定位：**保证开箱即用的基础功能，同时给足深度自定义的自由**——类似 GKD、壁纸引擎那种"官方给一套、社区/个人可以随意扩展和覆盖"的玩法。

第三方规则源让用户订阅自己信任的规则文件（社区维护的、或自己给内部软件写的），用来：认出官方规则库没收录的软件、补后台项目说明、显示"有新版"、以及一键更新。

### 核心原则
- **默认安全**：第三方默认不覆盖官方；危险口子都默认关、要用户亲手开。
- **充分自定义**：用户可以手动允许第三方规则覆盖官方规则（含 `signer`），实现深度客制化。
- **不碰的底线**：无论怎么自定义，从第三方规则安装前都有**醒目警告**，且安装器**照旧校验下载包的数字签名**与规则声明的 `signer` 一致——"再怎么自定义，也不会被静默装东西"。

### 本轮范围
- 添加/删除/启用/停用第三方源；每源「允许覆盖官方规则」开关；全局总开关。
- 下载（HTTPS）、解析（支持一个文件多条规则）、按信任与覆盖设置加载第三方规则。
- **新增一套可测试的确认对话框抽象**（安装前警告、各开关确认都走它）。
- 「规则」页的第三方源管理 UI；所有消费性开关的确认提示。

### 本轮明确不做
- **防篡改 / 签名验证**（用户决定第三方只走 HTTPS，不验签；留给以后或贡献者）。
- 源的清单(index)格式、源的自动发现、每条规则级别的单独开关（只做到每源粒度）。
- **编辑已有源的 URL**（改地址 = 删掉旧源 + 新加一个源；见 §6 对缓存的处理）。

## 2. 源模型

- **一个源 = 一个指向 YAML 文件的 URL**。
- 该 YAML 文件可含**一条或多条规则**：多条用 YAML 文档分隔符 `---` 隔开（现有官方规则文件都没用 `---`，向后兼容）。
- 传输只走 **HTTPS**，**不验签**。下载失败、解析失败只影响该源。
- 作者零工具：写好 yaml、托管到任意 https 地址即可。

## 3. 信任、覆盖与加载优先级

`RuleTrust { Official, ThirdParty }` 已存在。本功能要**重写** `RuleSetLoader` 的排序与去重逻辑（现有实现只有"官方/非官方"两档排序 + 写死的"第三方不能覆盖官方"警告，见 §11）。

### 3.1 优先级（三档）
同一次加载内，按下面的**排序键**决定谁先进 `byId`、谁在同 `id` 冲突时胜出（键小者优先）：

| 来源 | 排序键 |
|---|---|
| 开了「允许覆盖官方」的第三方源 | 0 |
| 官方 | 1 |
| 没开覆盖的第三方源 | 2 |

- 排序用**稳定排序**（LINQ `OrderBy` 即是），**同一档内保持传入顺序**。
- 因此要求：`RealBackend` 组装 sources 时，**第三方源严格按 `rule-sources.json` 里的数组顺序传入**，这样"多个开覆盖的源撞同一 id → 按添加顺序先到先得"才成立。

### 3.2 去重与警告文案（三类，分别准确表述）
遍历排好序的 sources，`byId` 里先到先得。命中已存在 id 时按下列情形给**不同**警告，不再用现有那句一刀切的"第三方不能覆盖官方"：

1. **官方规则被某个"开了覆盖"的第三方源顶掉**（`existing` 是开覆盖的第三方、`rule` 是官方）：
   警告"官方规则 {id} 已被你允许覆盖的第三方源 {源名} 覆盖"。**这是用户主动开启的预期行为，不是错误。**
2. **没开覆盖的第三方规则撞到官方 id**（`existing` 是官方、`rule` 是没开覆盖的第三方）：
   警告"第三方规则 {id} 与官方规则同名，未开启覆盖，已忽略"。官方保留。
3. **同档撞 id**（两个官方、或两个第三方同优先级撞）：
   警告"规则 {id} 与 {existing.SourceFile} 重复，已忽略"（先到先得）。

### 3.3 规则带上来源
每条规则加载后要能回答"我来自哪个源"：给 `Rule` 增加 `SourceUrl`、`SourceName`（见 §8），由 `RuleSetLoader` 按 `source` 填充。官方规则这两项为空。供安装前警告（§4）展示。

## 4. 安全护栏（底线，不随自定义改变）

- **安装前强警告**：当一次更新来自第三方规则时，确认对话框必须醒目显示：
  「此更新来自**未经审核的第三方规则源**」+ 来源 URL + 规则声明的发布者(`signer`)，用户确认才继续。
- **签名校验不放宽**：`RuleInstaller` 照旧下载安装包并校验其数字签名与规则 `signer` 一致，第三方规则也不例外、不跳过。
- 这两条对"开了覆盖"的第三方规则同样生效。

### 4.1 签名校验的保护边界（讲白残余风险）
`RuleInstaller` 校验的是"下载到的安装包，其数字签名的主体 == 规则里写的 `signer`"。
**它只保证"装的包确实由规则声明的那个发布者签名"，不保证该发布者本身可信。**
第三方规则完全可以把 `signer` 写成任意一个"有效签名但不是官方"的主体，并通过校验安装。
→ 因此对第三方（尤其开了覆盖的）而言，**真正的防线是安装前那个警告框**，签名校验只防"调包成未签名/别人签名的东西"。spec 行文不得让人以为签名校验本身证明了来源可信。

### 4.2 没有 `signer` 的第三方规则："能识别、不能一键装"
`RuleInstaller` 对**没写 `signer`（或没写 `installer.silentArgs`）** 的规则，在下载前就直接失败（现有行为，正确且不放宽）。社区/个人规则很可能只填 `update.latest`、不填 `installer`。
预期管理：
- 这类规则**仍参与识别、仍在更新列表里显示"有新版"**。
- 但 UI 要**提前把该条标成"该规则未声明签名者，无法一键安装"并禁用其安装入口**，而不是让用户点下去才报错（§9）。

## 5. 开关与确认提示

三个开关：
- **全局「启用第三方规则源」**（设置项；默认见 §6.3）。关掉它 = 回到纯官方规则状态。
- **每源「启用/停用」**。
- **每源「允许覆盖官方规则」**（默认关）。

**消费性改动必须弹确认框说明，不能点一下直接生效**（用户明确要求）：
- **关闭**全局总开关、**停用**某个源：确认框说明"这会停用你添加的第三方规则，相关软件可能变回认不出/不再提示更新"。
  （特例：当前一个源都没有时，关总开关无实际影响，可免确认或用更轻的文案。）
- **打开**某源「允许覆盖官方规则」：确认框说明"该源的规则将覆盖官方规则（含发布者校验目标），请确认你信任这个源"。
- 低风险动作（添加源时填 URL、关闭"允许覆盖"回到安全）可不强制二次确认；**删除一个源**要普通确认（防误删，且会清掉它的缓存，见 §6）。

所有确认框走 §11a 的 `IConfirmService`（WPF-UI 实现，**不触发任何阻塞式系统弹窗**）。

## 6. 存储

### 6.1 源列表
`%APPDATA%\UpdateHelper\rule-sources.json`，形如：

```json
{ "thirdPartyEnabled": true,
  "sources": [ { "id": "...", "url": "https://...", "note": "", "enabled": true, "allowOverrideOfficial": false } ] }
```

- `id`：由 `url` 派生的**稳定标识 = URL 的 SHA-256，十六进制小写字符串**（保证是合法、安全的目录名；不得用 Base64 等可能含 `/ + =` 的编码）。
- `note`：用户备注。
- `sources` 数组顺序即加载顺序（§3.1）。

### 6.2 下载缓存
- 路径：`%LOCALAPPDATA%\UpdateHelper\thirdparty-cache\<源id>\rules.yaml`（原样存下载到的 YAML）。
- 每源在自己的缓存目录里再存一份**同步状态**（如 `sync-state.json`：上次同步时间、结果、规则数），供 UI 每源展示（§9），参照官方 `RuleCacheStore` 的写法。
- 同步失败时**保留上次成功的缓存**（写新内容用"临时文件/目录整体替换"，失败不破坏旧的）。

### 6.3 默认值与坏数据
- **文件缺失或解析失败** → 一律回退到确定默认：`{ thirdPartyEnabled: true, sources: [] }`（§5 默认开 与 §6 坏数据回退在此对齐：回退后全局仍为 true，但无源时无实际影响）。读写坏数据**不抛异常**。

### 6.4 缓存清理（避免残留）
- **删除一个源**：同步删除它的 `thirdparty-cache\<id>\` 目录。
- **改 URL**（= 删旧源 + 加新源）：旧 id 的目录随"删旧源"一并清掉。
- **启动时孤儿清理**：扫描 `thirdparty-cache\` 下的子目录，凡 id 不在当前 `sources` 里的，删掉（兜底历史残留）。

## 7. 同步

- **共用触发时机，不共用同步实现**。官方同步是 `RuleSyncService`（下载 zip + .sig → 验签 → 防降级 → 替换缓存），**第三方不能复用它**；第三方要**另写一个同步服务**：对每个启用的源 HTTPS 下载单个 YAML → 存 `thirdparty-cache\<id>\rules.yaml`（**不验签**）→ 更新该源的 sync-state。
- 触发点（和官方同步挂在同样这三处，见 §11 代码落点）：
  1. 启动时一次；
  2. 每日自动一次（与官方共用调度判断窗口，但各自判重/各自状态）；
  3. 「规则」页「立即同步」。
- 对每个**启用**的源：任何失败（网络/解析/空）**只跳过它并记录到该源 sync-state**，不影响官方规则和其它源。
- 同步全程后台线程，不卡界面，不弹错误框（状态在「规则」页显示）。
- 第三方同步要有**自己的 `IsBusy`/重入保护**（现有 `RuleSubscriptionViewModel` 的 busy 只护官方同步）。

## 8. 加载链路与数据模型改动

### 8.1 `RuleSource` 最终形态
现为 `record RuleSource(string Directory, RuleTrust Trust)`，扩展为（新增字段给默认值，保证官方调用点不破）：

```csharp
sealed record RuleSource(
    string Directory,
    RuleTrust Trust,
    bool AllowOverrideOfficial = false,
    string SourceUrl = "",
    string SourceName = "");
```

每个已启用的第三方源映射成一个 `RuleSource`：`Directory = thirdparty-cache\<id>\`、`Trust = ThirdParty`、`AllowOverrideOfficial / SourceUrl(=url) / SourceName(=note 或 url)` 来自 `rule-sources.json`。

### 8.2 `Rule` 增加来源字段
`Rule` 增加 `SourceUrl`、`SourceName`（init 属性，默认空），`RuleSetLoader` 加载时按所属 `source` 填充。

### 8.3 多文档解析（关键：不要字符串 split）
- 现 `RuleParser.Parse` 用 `Deserializer.Deserialize<RuleDto?>(yaml)` 只读**单个**文档；`RuleSetLoader` 每文件只取一条。
- 新增**多文档解析入口**（如 `RuleParser.ParseAll(text, file)` 返回"多条规则 + 各自错误"）：**必须用 YamlDotNet 的 `YamlStream` / 流式 `Parser` 按 YAML 文档边界切分**，严禁用 `text.Split("---")`（`---` 可能出现在块标量/字符串值内部）。
- `RuleSetLoader` 改成按文件产出 **0..N 条**。
- **坏文档的粒度**：多文档文件里**某一条解析失败 → 只跳过该条并各记一条警告**，其余照常加载。
- **官方单文档行为不变**：单文档的 YAML 用同一多文档读取天然退化为 1 条。

### 8.4 两处加载都要含第三方（避免"能检测不能装"）
`RealBackend` 有**两处独立加载规则**，都要统一改为"官方 + 所有已启用第三方源"：
- `ScanAsync` → `LoadRules()`（识别/显示）。
- `InstallAsync` → **另起一次** `LoadRules()` 喂给 `RuleInstaller`（`RuleInstaller` 靠 `rules.Rules.FirstOrDefault(id)` 找规则，找不到就 `Fail`）。
→ 抽出统一的 sources 组装逻辑，两处共用；否则第三方更新"列表看得到、点安装找不到规则"。

### 8.5 安装前警告的数据链
- 更新候选 `UpdateCandidate.PackageId = "rule:" + rule.Id`（现有）。
- 确认时：ViewModel 持有 `Snapshot.Rules`，用去掉 `rule:` 前缀的 id 反查 `Rule`，读 `Trust` / `SourceUrl` / `SourceName` / `Update.Signer`，组装警告文案。
- `UpdatesViewModel` 当前只引用 `_state.Updates`、不持有 `Snapshot` —— 需让它能拿到 `Snapshot.Rules`（经 `AppState`）。

## 9. 界面（「规则」页）

在现有官方源卡片下方加「第三方规则源」区：
- 顶部：全局「启用第三方规则源」开关（关闭走确认框）+ 一句 **"第三方源未经审核，内容和更新包都由对方负责，风险自负"** 的常驻提示。
- 列表：每个源一行——备注/URL、规则数、上次同步状态（来自该源 sync-state）、「启用」开关、「允许覆盖官方」开关（打开走确认框）、删除按钮（普通确认，会清缓存）。
- 对"规则缺 `signer`/`silentArgs`、无法一键安装"的第三方规则，在相关处给可读提示（§4.2），不是点了才报错。
- 底部：「添加源」——输入 URL（可选备注），校验是 https 再加入；加入后立即尝试同步一次。
- 所有确认框用 §11a 的 `IConfirmService`（WPF-UI 对话框，**不触发**任何会阻塞的系统级弹窗）。
- 遗留收敛：现存 `SoftwarePage.xaml.cs` 的阻塞式 `MessageBox` 与 §9 原则冲突；新确认服务建立后，**顺带把它替换成 `IConfirmService`**，避免两套并存。

## 10. 测试

- 加载优先级：官方 vs 第三方（不覆盖/覆盖）、多个覆盖源撞 id（按添加顺序先到先得）、坏 YAML 跳过、**三类去重警告文案各一例**。
- 多文档：一个文件多条(`---`)拆成多条、其中一条坏只跳该条、单文档退化为一条、`---` 出现在字符串值里不被误切。
- 源配置存取：rule-sources.json 往返、**文件缺失→默认 `{true, []}`**、坏数据回退、enabled/allowOverride/顺序字段。
- 同步：假下载器——某源失败只跳过它、其余正常；缓存保留上次成功；每源 sync-state 落盘。
- 缓存清理：删源清目录、孤儿目录启动清理。
- 第三方来源标注：加载后能从规则拿到 `SourceUrl`；安装前能组出"第三方 + 源 URL + signer"文案。
- **两处加载都含第三方**：断言第三方规则能走进 `RuleInstaller`（而非"找不到规则"）。
- 安装护栏：第三方规则走安装器仍校验签名（复用现有 RuleInstaller 测试思路，断言不跳过）；无 signer 的第三方规则被标为"不能一键装"。
- 确认服务：`IConfirmService` 可用假实现单测——开关状态→确认文案→确认/取消分支（关总开关、停用源、开覆盖、删除源、安装第三方）。
- 真实网络不进单测；真机端到端手动验一次（加一个源、同步、看到规则、覆盖开关、安装警告、无 signer 提示、删源清缓存）。

## 11. 与现有代码的落点

- **复用**：`RuleTrust`、`RuleParser`（扩展出多文档入口）、`IDownloader`/`HttpDownloader`、现有「规则」页与同步**触发点**、`RuleInstaller` 的签名校验、`RuleCacheStore` 的"临时替换+失败不抛"写法做参照。
- **改写**：`RuleSetLoader`（三档排序 + 三类去重警告 + 多文档 + 填来源）、`RuleSource`（加字段）、`Rule`（加 `SourceUrl/SourceName`）、`RealBackend.LoadRules`（两处都含第三方，抽公共组装）。
- **新增**：
  - **§11a 确认对话框抽象**：`IConfirmService.ConfirmAsync(标题, 正文) → Task<bool>`，放 `UpdateHelper.Presentation`（ViewModel 可注入假实现单测），`UpdateHelper.App` 用 WPF-UI `ContentDialog` 实现并接线。安装流程 `UpdatesViewModel.InstallSelectedAsync` 改为"（第三方条目）先弹警告再装"。**当前安装流程完全没有确认步骤，这是从零新建的一套机制，不是"复用"。**
  - 第三方源配置存储（读写 rule-sources.json + 默认/坏数据回退 + 缓存清理）。
  - 第三方同步服务（下载 yaml → thirdparty-cache，不验签，每源状态，自己的 busy）。
  - 「规则」页第三方 UI、确认框接线、无 signer 提示。
- **同步触发点的具体位置**（第三方同步要挂到这几处，目前它们只调官方 `backend.SyncRulesAsync`）：启动时 `App.xaml.cs` 的启动同步、每分钟 tick 的定时同步、`RulesPage` 的「立即同步」→ `RuleSubscriptionViewModel.SyncAsync`。建议新增 `IAppBackend.SyncThirdPartyAsync` 并在这三处与官方同步并列调用。
- **每日调度并存**：官方与第三方可共用同一个 24h 判断窗口，但**各自判重、各自落盘状态、各自 UI 展示**。
- 不涉及提权，与搁置的后台助手无关。
- **偏离旧 spec**：`2026-09-30` 主文档 §8 曾写"第三方规则不能放宽官方 signer"——本设计按用户新决定改为"**默认不覆盖，用户手动开启后可覆盖**"，并以安装前强警告 + 签名校验（边界见 §4.1）兜底。
